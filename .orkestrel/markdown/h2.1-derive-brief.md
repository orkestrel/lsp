## Defect 1 — the derivation chain crosses into another node

The objective lane's public counterexample, which your failing proof reproduces:

- Parse `a\n\nb\n\nc`, yielding source paragraph nodes `A`, `B`, and `C`.
- A `map` replaces both `A` and `B` with one shared identity `S`. `S` correctly reports no span,
  because it derives from separate sources.
- A chained `map` replaces each `S` with a shared `T`, and replaces `C` with `S`.
- `rewriteDocument` records `T → S` and `S → C` (`src/core/helpers.ts:3072`).
- `#derive` follows `T → S → C` and assigns `C`'s `{6,7}` span to `T` (`src/core/Markdown.ts:217`).

The walk terminates. The answer is another node's region. The derivation map conflates an
identity's role as an INPUT hop with its separate role as an OUTPUT elsewhere in the same
rewrite, and the resolution must not cross that boundary.

The exact rule is yours to design, under these constraints: the source-first order the design
record fixed stays; the walk still terminates for every chain the public API can build; an
identity that legitimately retains its source's span keeps answering with it; and where the
correct answer cannot be established, the method answers `undefined` rather than guessing.
State the rule you chose and why in your report.

## Defect 2 — the zero-width boundary picks the earlier segment

For this source:

```ts
{
  text: 'ab',
  segments: [
    { offset: 0, start: 0, end: 1 },
    { offset: 1, start: 5, end: 6 },
  ],
}
```

`projectSpan(source, 1, 1)` returns `{ start: 1, end: 1 }` because the first segment accepts
`from <= limit` and returns immediately (`src/core/helpers.ts:236`). The documented segment
contract puts derived position `1` in the second run, so the answer is `{ start: 5, end: 5 }`.

Fix the early return so a zero-width position on a boundary resolves to the later segment.
`sliceSource` boundary arithmetic is CONFIRMED CORRECT by the audit and needs no change; do not
alter it.

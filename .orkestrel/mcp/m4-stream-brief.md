## The implementation, precisely

### 1. `matchesSubscriptionNotification` (`src/core/helpers.ts`)

Add one branch, after the existing `resources/updated` branch, for the tasks family. The
admission path treats a producer frame as foreign input: gate with `isMCPTaskNotification`
before reading `params.taskId`, so a malformed or mutated producer snapshot never reaches
the wire.

```ts
if (notification.method === 'notifications/tasks') {
	return isMCPTaskNotification(notification) && filter.taskIds?.includes(notification.params.taskId) === true
}
```

Import `isMCPTaskNotification` into the existing `from './validators.js'` import block in
`helpers.ts` (it already imports `isBoundedString`, `isJSONRPCId`, `isJSONRPCNotification`,
`isMCPInputResult`, `isMCPLegacyVersion`, `isMCPMetaObject`, `isMCPTaskResult` from there).

### 2. `buildSubscriptionFilter` (`src/core/helpers.ts`) — the `tasks: boolean` parameter

Add a third parameter, **defaulted to `false`**, so the one existing call site in
`tests/src/core/helpers.test.ts:533` (a file you do not own and do not edit) keeps
type-checking and keeps its current behavior unchanged:

```ts
export function buildSubscriptionFilter(
	requested: MCPSubscriptionFilter,
	supported: MCPSubscriptionFilter,
	tasks = false,
): MCPSubscriptionFilter {
```

The supported side has no honest spelling for "any task id" (unlike
`resourceSubscriptions`, which intersects against a concrete supported set) — `tasks` is
the boolean gate the boolean-behavior law calls for. When `tasks` is `true`, pass
`requested.taskIds` through unfiltered by this function (entitlement resolution happens
in `MCPServer.ts`, step 4 below, not here — this function stays a pure intersection).
Follow the existing pattern for including a member only when it is a non-empty array:

```ts
const taskIds = tasks ? requested.taskIds : undefined
...
...(taskIds !== undefined && taskIds.length > 0 ? { taskIds } : {}),
```

### 3. The derived support fact (`src/core/MCPServer.ts`)

In `#subscription` (around line 1332, where `buildSubscriptionFilter` is currently
called with two arguments), derive whether the server can push tasks from existing state
— no new flag, no third field:

```ts
const task = this.#options.task
const configured = this.#options.subscription
const tasks = task !== undefined && configured !== undefined
const notifications = buildSubscriptionFilter(requested, configured?.notifications ?? {}, tasks)
```

This mirrors the existing `const configured = this.#options.task; if (configured ===
undefined) return` pattern at `MCPServer.ts:356-359` — the fact that a handler is
registered at all already proves `task` was configured at construction, and this is the
same style of derivation, not a new one.

### 4. Authorize-and-omit acknowledgement (`src/core/MCPServer.ts`)

Between computing `notifications` (step 3) and `yield buildSubscriptionAcknowledgement(notifications, id)`,
resolve each requested task identifier through `MCPTaskManagerInterface.task(id, options)`
and replace `notifications.taskIds` with exactly the resolved subset, in request order,
with no deduplication:

- **Authorizes**: an identifier resolves only if `task.tasks.task(id, options)` returns
  something other than `undefined`.
- **Omits with no distinguishing signal**: an identifier that does not resolve — never
  existed, was purged, or the caller is unauthorized (the port's own `task(id, options)`
  contract collapses all three into the same `undefined`, per
  `/home/user/mcp/src/core/types.ts:861-869`) — is left out of the acknowledged set with
  no error and no other marker.
- **Preserves order, does not normalize duplicates**: iterate `notifications.taskIds` in
  its given order; if the caller listed the same id twice, both resolved copies stay.
- **Fixes the agreed set for the subscription's lifetime**: the SAME resolved filter
  object (not a re-derived one) is the value acknowledged AND the value passed to every
  later `matchesSubscriptionNotification` call in this subscription's delivery loop. No
  further `task(id, options)` call happens once the stream starts delivering — a per-frame
  store read at delivery time re-creates, on every event, the resolution the
  acknowledgement already did once, and the reconciliation rules this out explicitly.
- **Omits the member entirely when the server cannot push tasks**: this falls out of step
  2/3 without further code — when `tasks` is `false`, `notifications.taskIds` is already
  `undefined` and this resolution step has nothing to do.

Sketch (adapt to the existing method's control flow and naming; do not introduce a new
public method or export unless the existing private-method style in this class already
calls for one):

```ts
let notifications = buildSubscriptionFilter(requested, configured?.notifications ?? {}, tasks)
const requestedTaskIds = notifications.taskIds
if (requestedTaskIds !== undefined) {
	const resolved: string[] = []
	if (task !== undefined) {
		for (const taskId of requestedTaskIds) {
			if ((await task.tasks.task(taskId, options)) !== undefined) resolved.push(taskId)
		}
	}
	const { taskIds: _dropped, ...rest } = notifications
	notifications = resolved.length > 0 ? { ...rest, taskIds: resolved } : rest
}
yield buildSubscriptionAcknowledgement(notifications, id)
```

Use `options: MCPMethodOptions` — the same options object already threaded through
`#subscription` — as the second argument to `task(id, options)`, matching every other
`tasks/*` handler's call convention in this file (see the `#task`, `#update`, `#abort`
registrations a few lines above).

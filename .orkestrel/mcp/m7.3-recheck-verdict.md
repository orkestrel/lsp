# Findings outside the claims

## F1. A pure formatter shipped as a private method

`src/server/transports/HTTPClientTransport.ts:227-240` declares `#responseError(response, type)`, which reaches no `#` field and no sibling method and does nothing but format a message. `.claude/rules/architecture.md` § Functions and orchestration reserves a `#` method for stateful or instance-bound orchestration and sends a pure self-contained format to an exported helper; every other private method in this file (`#exchange`, `#deliver`, `#buildHeaders`, `#capture`) reads state, so this one is the outlier. Nothing mechanical catches it — the policy sweep reads module scope only — so review is the instrument the rules name for it.

Right looks like: export it from `src/server/helpers.ts` as `buildResponseError(response, type)`, call it from `#deliver`, and give it rows over the three shapes it formats.

## F2. The transport throws into its own catch and rebuilds the error

`src/server/transports/HTTPClientTransport.ts:204-224` throws `#responseError(...)` at `:208`, `:217`, and `:220` inside a `try` whose own `catch` at `:221` discards the caught value and constructs an identical error again at `:222`. Every error object built inside the `try` is dead. A reader has to trace the throw into the catch and back out before concluding that `send` rejects, and the duplicated `!response.ok` decision now appears four times in twenty lines.

Right looks like: keep the `try` around the decode alone, and take the `!response.ok` decision once after it — decode failure on a success response emits `error`, and any non-success response with no captured message throws once.

## F3. `#methods` no longer names what it holds

`src/core/MCPLegacyClientTransport.ts:59` changed `#methods` from `Map&lt;JSONRPCId, string&gt;` to `Map&lt;JSONRPCId, readonly [method: string, deadline: AbortSignal]&gt;`. The field name described the old contents exactly and describes the new contents not at all — the commit message, the class TSDoc at `:49-50`, and the report all call these "correlations". `.claude/rules/architecture.md` and the naming law both want the term that survived the change to be the one in the code.

The tuple's second element compounds it: `correlation[1]` is read once, at `:131`, on the value the closure already holds, and is never read back out of the map. The map needs an identity token, which the tuple provides, but the `deadline` slot is state with no reader.

Right looks like: rename the field `#correlations`, and store the method under a token the identity check can compare — dropping the never-read signal from the stored value — so the positional `correlation[0]` reads at `:325` disappear with it.

## F4. The adapter's new failure surface has no coherent code and no guide

The adapter now answers a consumer with wire codes it chose in this change, and the choices disagree with each other and with the fault. `src/core/MCPLegacyClientTransport.ts:281` answers `JSONRPC_INVALID_PARAMS` (`-32602`) for "has not completed its handshake", which is a state error rather than a parameter error; `:334` answers the same `-32602` for `Legacy MCP peer returned a malformed result`, telling the caller its own request carried invalid params when the peer's answer was at fault; and `:139` answers `JSONRPC_INTERNAL_ERROR` (`-32603`) for the deadline. One class of failure — the adapter cannot serve this correlated request — leaves through three doors under two codes, one of which misdescribes who erred.

None of it reaches `guides/mcp.md`. The adapter section documents the handshake refusals and now the forwarded-request deadline (`:1698-1700`), but never says that a consumer driving the adapter receives correlated JSON-RPC errors, nor which codes. `.claude/rules/documentation.md` § Parity puts public behavior in the guide, and the unit owned that file.

Right looks like: answer every adapter-owned refusal with `JSONRPC_INTERNAL_ERROR`, keeping `-32602` for a fault in what the caller sent, and state in the adapter section which correlated errors the adapter itself produces and when.

## F5. The `close()` clear of `instructions` is pinned by nothing

`src/core/MCPLegacyClientTransport.ts:155` clears `#instructions` on close, and `:248` assigns it unconditionally on every accepted handshake. The row that claims the clear — `preserves legacy instructions in discovery and clears them across reconnect` — reconnects to a peer whose second handshake omits the field, so `:248` alone makes it green and deleting `:155` leaves it green. The row proves the projection leg it was written for; the clear is a line no test reaches.

Right looks like: assert the clear where only `close()` can produce it — read discovery after `disconnect()` and before the next handshake, or drive the adapter directly across `close()`.

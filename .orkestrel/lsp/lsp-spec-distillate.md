# LSP 3.18 distillate (staged primary sources)

Sources: `tmp/cursor/sources/lsp-3.18-specification.html` (authoritative 3.18 page; fetched 2026-08-25), `tmp/cursor/sources/lsp-3.18-metaModel.json` (`metaData.version` `3.18.0`), `tmp/cursor/sources/lsp-3.18-specification.md` (Jekyll shell: “What’s new in 3.18” prose only), `tmp/cursor/sources/lsp-overview.html` (architecture framing).

Overview framing (`What is the Language Server Protocol?`, `How it works`): a language server is a separate process; a tool talks to it over JSON-RPC. The protocol is document-URI and position based, not an AST or compiler-symbol model. A typical session uses `textDocument/didOpen`, `textDocument/didChange`, `textDocument/publishDiagnostics`, `textDocument/definition`, and `textDocument/didClose`. After `didOpen`, document truth lives in the tool’s memory, not on disk. The spec itself (`languageServerProtocol`) currently assumes one server serves one tool; sharing a server across tools is undefined.

The 3.18 page states it describes the current 3.18.x version and is under development.

## Base protocol

**Framing** (`baseProtocol`, `headerPart`, `contentPart`). A message is a header part plus a content part, separated by `\r\n`. Header fields are `Name: value` terminated by `\r\n`, HTTP-style (RFC 7230 §3.2). At least one header is mandatory, so two `\r\n` sequences always precede content. Supported fields: `Content-Length` (required; content length in bytes) and `Content-Type` (optional; default `application/vscode-jsonrpc; charset=utf-8`). The header, including the separator, is ASCII. Content is JSON-RPC 2.0, encoded as the `Content-Type` charset, default `utf-8` (the only encoding supported now). A non-`utf-8` charset should produce an error. The legacy constant `utf8` should be treated as `utf-8`.

**JSON-RPC shape** (`contentPart`, `abstractMessage`, `requestMessage`, `responseMessage`, `notificationMessage`). `jsonrpc` is always `"2.0"`. Batch messages are not supported. Request: `id` (`integer | string`), `method`, optional `params` (`array | object`). Every processed request must get a response. Response: `id` (`integer | string | null`), optional `result` (`LSPAny`; required on success, must not exist on error), optional `error` (`ResponseError`: `code`, `message`, optional `data`). If a request has no result value, `result` should be `null`. Notification: `method` plus optional `params`; must not produce a response. Parameters of protocol requests/notifications should be objects if present; custom messages may use arrays.

**Error codes** (`errorCodes`). JSON-RPC: `ParseError` `-32700`, `InvalidRequest` `-32600`, `MethodNotFound` `-32601`, `InvalidParams` `-32602`, `InternalError` `-32603`. JSON-RPC reserved range: `jsonrpcReservedErrorRangeStart` `-32099` through `jsonrpcReservedErrorRangeEnd` `-32000` (not real codes; no LSP codes should be defined in this range). Historical occupants of that range: `ServerNotInitialized` `-32002` (request/notification before `initialize`), `UnknownErrorCode` `-32001`. Deprecated aliases: `serverErrorStart` / `serverErrorEnd`. LSP reserved range: `lspReservedErrorRangeStart` `-32899` through `lspReservedErrorRangeEnd` `-32800`. LSP codes: `RequestFailed` `-32803` (since 3.17.0; syntactically valid but failed), `ServerCancelled` `-32802` (since 3.17.0; only for explicitly server-cancellable requests), `ContentModified` `-32801` (document modified outside normal conditions; a server should **not** send this merely because an unprocessed change sits in its queue), `RequestCancelled` `-32800` (client cancel detected; this value equals the LSP range end).

**`$` methods** (`dollarRequests`). Methods starting with `$/` are implementation-dependent. A `$/` notification may be ignored. A `$/` request must be rejected with `MethodNotFound` (`-32601`).

**Cancellation** (`cancelRequest`). Notification ` $/cancelRequest` with `CancelParams.id` (`integer | string`). A canceled request still must return a response (JSON-RPC). Partial results on cancel are allowed. An error response on cancel is advised to use `ErrorCodes.RequestCancelled`.

**Ordering** (`messageOrdering`). Responses should be sent in roughly request order. Reordering is allowed when it does not affect correctness (example given: `textDocument/completion` vs `textDocument/signatureHelp`). Reordering that can affect correctness is not (example given: `textDocument/definition` vs `textDocument/rename`).

## Lifecycle

**Server lifetime** (`lifeCycleMessages`). The client manages process start and shutdown.

**`initialize`** (`initialize`, `initializeParams`, `initializeResult`, `clientCapabilities`, `serverCapabilities`). Method `initialize`, params `InitializeParams` (extends `WorkDoneProgressParams`). It is the first request and may be sent only once. Before `initialize`: a request should error with `-32002`; notifications should be dropped except `exit`. Until the server answers with `InitializeResult`, the client must send no further requests or notifications. Until that response, the server may send only `window/showMessage`, `window/logMessage`, `telemetry/event`, and `window/showMessageRequest`; if `workDoneToken` is set on initialize params, the server may also send `$/progress` for that token only.

`InitializeParams` includes `processId` (`integer | null`; if the parent is not alive the server should exit), optional `clientInfo`, optional `locale` (IETF language tag, since 3.16.0), deprecated `rootPath` / `rootUri` (`rootUri` wins if both set; `rootUri` deprecated in favour of `workspaceFolders`), optional `initializationOptions`, `capabilities: ClientCapabilities`, optional `trace`, optional `workspaceFolders`.

`ClientCapabilities` groups `workspace`, `textDocument`, `notebookDocument` (since 3.17.0), `window`, `general` (since 3.16.0), and `experimental`. Unknown client-capability properties should be ignored. A missing property means the capability is absent. Client capabilities describe 3.x+ features; 2.x capabilities remain mandatory (omitting `textDocument.synchronization` does not opt out of open/change/close). Clients should ignore server capabilities they do not understand.

`InitializeResult` carries `capabilities: ServerCapabilities` and optional `serverInfo`. `ServerCapabilities` includes `positionEncoding` (since 3.17.0; default `utf-16`), `textDocumentSync`, `notebookDocumentSync`, feature providers (`completionProvider`, `hoverProvider`, …), `inlineCompletionProvider` (since 3.18.0), `workspace` (`WorkspaceOptions`: `workspaceFolders`, `fileOperations`, `textDocumentContent` since 3.18.0), and `experimental`.

**`initialized`** (`initialized`). Client → server notification after receiving `InitializeResult` and before any other client request/notification. Params `InitializedParams` (empty). May be sent only once. The server may dynamically register capabilities here.

**Dynamic registration** (`client_registerCapability`, `client_unregisterCapability`). Server → client request `client/registerCapability` with `RegistrationParams.registrations[]` (`id`, `method`, optional `registerOptions`). A client opts in per-capability via `dynamicRegistration`. A server must not register the same capability both statically (initialize result) and dynamically for the same document selector. `client/unregisterCapability` uses `UnregistrationParams.unregisterations` (the misspelling is acknowledged as a breaking-change hold until 4.x). `StaticRegistrationOptions.id` allows later unregistration of a statically registered feature. `TextDocumentRegistrationOptions.documentSelector` may be `null` to use the client-side selector.

**`shutdown` / `exit`** (`shutdown`, `exit`). `shutdown` is a request with no params; result `null`. The server must not exit yet. After `shutdown`, clients must send no requests/notifications other than `exit`, and should wait for the shutdown response before sending `exit`. Requests after shutdown should error with `InvalidRequest`. `exit` is a notification with no params. Exit code 0 if `shutdown` was received; otherwise 1.

**Trace** (`setTrace`, `logTrace`, `traceValue`). `$/setTrace` / `$/logTrace`; `TraceValue` is `'off' | 'messages' | 'verbose'`.

## Progress model

**Generic progress** (`progress`, since 3.15.0). Notification `$/progress` with `ProgressParams<T>`: `token: ProgressToken` (`integer | string`) and `value: T`. The token is not the request id, so progress can be out of band and can apply to notifications.

**Work done progress** (`workDoneProgress`, since 3.15.0). Reported as `$/progress` whose value is one of three payloads.

- Begin (`workDoneProgressBegin`): `kind: 'begin'`; mandatory `title`; optional `cancellable` (whether a cancel button should be shown; clients that lack cancellation may ignore it); optional `message` (if unset, a previous message stays valid); optional `percentage` (`uinteger`, range `[0, 100]`; 100 means 100%). If `percentage` is omitted, infinite progress is assumed and clients may ignore later percentages. Values should rise steadily; clients may ignore non-monotonic values.
- Report (`workDoneProgressReport`): `kind: 'report'`; optional `cancellable` (only valid if begin requested a cancel button); optional `message`; optional `percentage` (same rules as begin). No `title`.
- End (`workDoneProgressEnd`): `kind: 'end'`; optional `message` (final outcome).

**Initiation** (`initiatingWorkDoneProgress`).

*Client-initiated* (`clientInitiatedProgress`, `workDoneProgressParams`). The request sender (mostly clients) puts `workDoneToken?: ProgressToken` on the request params. Example: `textDocument/reference` params include `workDoneToken`. The server reports `$/progress` with that token. The token is valid only until the request has sent a response. Canceling work-done progress is done by canceling that request. There is no static client capability for per-request tokens; presence of `workDoneToken` on that request instance is the signal. To avoid a client UI with no reports, the server must advertise general support via `WorkDoneProgressOptions.workDoneProgress` on the corresponding server capability (example: `referencesProvider: { workDoneProgress: true }`).

*Server-initiated* (`serverInitiatedProgress`, `window_workDoneProgress_create`, `window_workDoneProgress_cancel`). The server sends `window/workDoneProgress/create` (`WorkDoneProgressCreateParams.token`). Allowed only if the client sets `window.workDoneProgress`. Useful outside a request (example: re-indexing). The create token should be used once: one begin, many report, one end. If create errors, the server must not send progress for that token. `window/workDoneProgress/cancel` is a client → server notification (`WorkDoneProgressCancelParams.token`). The progress need not be marked `cancellable`; a client may cancel for any reason (error, workspace reload, …).

**Partial results** (`partialResults`, `partialResultParams`, since 3.15.0). Also `$/progress`. The value is usually the same type as the final result (example: `workspace/symbol` partials are `SymbolInformation[] | WorkspaceSymbol[]`). The client opts in by putting `partialResultToken` on the request (alongside `workDoneToken` if both apply). If the server reports any partials via `$/progress`, the **whole** result must be reported that way (each notification appends); the final response must be empty of result values. On error: if `code` is `RequestCancelled`, the client may use the partials but should make cancellation/incompleteness clear; otherwise the partials should not be used.

## Document synchronization

**Ownership and mandatoriness** (`textDocument_synchronization`). Client support for `textDocument/didOpen`, `textDocument/didChange`, and `textDocument/didClose` is mandatory, including full and incremental `didChange`. A server must implement all three or none. Opting out only makes sense for read-only documents. Client capability: `textDocument.synchronization.dynamicRegistration`. Server: `textDocumentSync` as `TextDocumentSyncKind | TextDocumentSyncOptions`. `TextDocumentSyncKind`: `None` `0`, `Full` `1`, `Incremental` `2`. `TextDocumentSyncOptions`: `openClose?`, `change?` (default `None` if omitted). If `textDocumentSync` is omitted on the server, it defaults to `None`.

**`didOpen`** (`textDocument_didOpen`). Client → server. After this, the client manages content; the server must not read via the URI. Open/close must be balanced; max open count per document is one. Language-id change: `didClose` then `didOpen` with the new id. Ability to fulfill requests is independent of open/closed. Params: `DidOpenTextDocumentParams.textDocument: TextDocumentItem` (`uri`, `languageId`, `version`, content).

**`didChange`** (`textDocument_didChange`, `textDocumentContentChangeEvent`). Requires prior `didOpen`. Before information requests (`completion`, `signatureHelp`, …), the client must have synchronized document state. `DidChangeTextDocumentParams`: `textDocument: VersionedTextDocumentIdentifier` (version is **after** all listed changes) and `contentChanges: TextDocumentContentChangeEvent[]`. Changes in one notification apply in order, each on the state produced by the previous. `TextDocumentContentChangeEvent` is `TextDocumentContentChangePartial` (`range`, deprecated `rangeLength?`, `text`) **or** `TextDocumentContentChangeWholeDocument` (`text` only = full content). Sync kind `Full` vs `Incremental` selects which form is used. Dynamic registration uses `TextDocumentChangeRegistrationOptions.syncKind`.

**Versioning** (`textDocumentItem`, `versionedTextDocumentIdentifier`, `optionalVersionedTextDocumentIdentifier`). Version increases after each change including undo/redo; it need not be consecutive. Server → client optional version may be `null` when the file is not open and disk is master.

**`willSave` / `willSaveWaitUntil` / `didSave` / `didClose`** (`textDocument_willSave`, `textDocument_willSaveWaitUntil`, `textDocument_didSave`, `textDocument_didClose`). `willSave`: notification with `WillSaveTextDocumentParams` (`textDocument`, `reason`: `Manual` 1, `AfterDelay` 2, `FocusOut` 3). Client cap `textDocument.synchronization.willSave`; server `textDocumentSync.willSave`. `willSaveWaitUntil`: request, same params, result `TextEdit[] | null`; clients may drop slow/failing results. `didSave`: notification; optional `text` if `SaveOptions.includeText`. Client cap `textDocument.synchronization.didSave`; server `textDocumentSync.save`. `didClose`: after this, master is where the URI points (disk for `file:`). Requires a prior open. Content ownership transfers back.

**Position encoding** (`textDocuments`, `position`, `positionEncodingKind`, `generalClientCapabilities`). Positions are zero-based line and character offset; a position sits between characters. Specials such as `-1` are not supported. Character greater than line length defaults to line length. EOL sequences: `\n`, `\r\n`, `\r`. Positions are line-end agnostic (cannot denote `\r|\n` or `\n|`). Before 3.17, offsets were always UTF-16 code units (example: in `a𐐀b`, `a` is 0, `𐐀` is 1, `b` is 3). Since 3.17 the client offers `general.positionEncodings` (preference order). `utf-16` is mandatory; if missing from the client array, servers may assume UTF-16. Server picks via `capabilities.positionEncoding`; omit → `utf-16`. Kinds: `utf-8` (UTF-8 code units/bytes), `utf-16` (default; servers must always support), `utf-32` (UTF-32 code units / Unicode code points). Conversion is best done where the file is read, usually on the server.

**`Position` / `Range` / `Location` / `DocumentUri`** (`position`, `range`, `location`, `uri`, `documentUri`). `Range`: exclusive end; to include a line’s ending, use start-of-next-line as end. `Location`: `{ uri: DocumentUri, range: Range }`. `DocumentUri` is a string that must parse as a URI (RFC 3986). Encoding of drive letters is not uniform (`file:///c:/…` vs `file:///C%3A/…`); parties must not assume matching encoding or casing.

## Structure-bearing language features

**`textDocument/documentSymbol`** (`textDocument_documentSymbol`, `documentSymbol`, `symbolInformation`, `symbolKind`). Client cap `textDocument.documentSymbol` (`hierarchicalDocumentSymbolSupport`, `symbolKind.valueSet`, `tagSupport`, `labelSupport`). Server cap `documentSymbolProvider`. Params: `DocumentSymbolParams` (work-done + partial). Result: `DocumentSymbol[] | SymbolInformation[] | null` (not mixed; first partial chunk fixes the type). Servers should prefer hierarchical `DocumentSymbol` (`name`, optional `detail`, `kind`, optional `tags`, deprecated `deprecated`, `range`, `selectionRange`, optional `children`). Flat `SymbolInformation` is deprecated (`location` + optional `containerName`; neither may be used to reconstruct hierarchy). `SymbolKind`: `File` 1 … `TypeParameter` 26. `SymbolTag.Deprecated` 1.

**`textDocument/foldingRange`** (`textDocument_foldingRange`, `foldingRange`). Result `FoldingRange[]` (partial same). `FoldingRange`: `startLine`/`endLine` (zero-based); optional `startCharacter`/`endCharacter`; optional `kind`; optional `collapsedText` (since 3.17.0). Client `lineFoldingOnly` ignores character offsets. Refresh (`workspace_foldingRange_refresh`, since 3.18.0, `@proposed` on `workspace.foldingRange.refreshSupport`): server → client `workspace/foldingRange/refresh`, params none, result void.

**`textDocument/selectionRange`** (`textDocument_selectionRange`, `selectionRange`, since 3.15.0). Params: document + `positions[]`. Result `SelectionRange[] | null` aligned by index; `positions[i]` must be in `result[i].range`; empty range at the position is allowed when there is no range. `SelectionRange`: `range` plus optional `parent` (`parent.range` must contain `this.range`). Typically corresponds to syntax-tree nodes. Client cap `textDocument.selectionRange`; server `selectionRangeProvider`.

**`textDocument/semanticTokens`** (`textDocument_semanticTokens`, `semanticTokensLegend`, `semanticTokens`, since 3.16.0). Legend: `tokenTypes[]` / `tokenModifiers[]` (index and bit flags). Format `relative` only (`tokenFormat`). Each token is five integers at `5*i … 5*i+4`: `deltaLine`, `deltaStart`, `length`, `tokenType` (`< 65536`), `tokenModifiers` (bitmask). `deltaStart`/`length` use the negotiated position encoding. Multiline/overlap gated by `multilineTokenSupport` / `overlappingTokenSupport`. Methods: `textDocument/semanticTokens/full` → `SemanticTokens | null` (`resultId?`, `data: uinteger[]`); `textDocument/semanticTokens/full/delta`; `textDocument/semanticTokens/range`; refresh `workspace/semanticTokens/refresh`. Client request options: `range?`, `full?` / `full.delta?`. Server cap `semanticTokensProvider` with `legend`, `range?`, `full?`. Token type `label` is since 3.18.0. No resolve-provider on this feature.

**`textDocument/inlayHint`** (`textDocument_inlayHint`, `inlayHint`, since 3.17.0). Params: document + visible `range`. Result `InlayHint[] | null`. `InlayHint`: `position`, `label` (string or `InlayHintLabelPart[]`, neither empty), optional `kind`, `textEdits`, `tooltip`, padding, `data`. **Resolve:** server `inlayHintProvider.resolveProvider`; client `textDocument.inlayHint.resolveSupport.properties`. Method `inlayHint/resolve`. Tooltip/`textEdits` may be filled lazily.

**`textDocument/documentLink`** (`textDocument_documentLink`, `documentLink`). Params: document. Result `DocumentLink[] | null`. `DocumentLink`: `range`, optional `target` (missing → resolve later), optional `tooltip` (since 3.15.0), optional `data`. **Resolve:** server `documentLinkProvider.resolveProvider`; method `documentLink/resolve`.

**Resolve-provider pattern on this surface.** Lazy resolve appears on `documentLink` (`documentLink/resolve`, `resolveProvider`, `data`) and `inlayHint` (`inlayHint/resolve`, `resolveProvider`, client `resolveSupport.properties`). Document symbols, folding ranges, selection ranges, and semantic tokens have no resolve request.

## Diagnostics

**Push** (`textDocument_publishDiagnostics`). Server → client notification. Diagnostics are owned by the server; newly pushed diagnostics always replace previous ones for that URI (no client merge). Empty array clears. VS Code-oriented rule stated: single-file languages clear on close; project languages do not. Recompute on change is the server’s job. Params: `uri`, optional `version` (since 3.15.0; client `versionSupport`), `diagnostics[]`. Client cap `textDocument.publishDiagnostics` (`relatedInformation`, `tagSupport`, `versionSupport`, `codeDescriptionSupport`, `dataSupport`).

**Pull** (`textDocument_pullDiagnostics`, `textDocument_diagnostic`, `workspace_diagnostic`, since 3.17.0). Client cap `textDocument.diagnostic`; server `diagnosticProvider` (`DiagnosticOptions`: optional `identifier`, `interFileDependencies`, `workspaceDiagnostics`). Document pull `textDocument/diagnostic`: params include `textDocument`, optional `identifier`, optional `previousResultId`; result `DocumentDiagnosticReport` = related full (`kind: 'full'`, optional `resultId`, `items`) or related unchanged (`kind: 'unchanged'`, required `resultId`; allowed only if result ids were provided). Workspace pull `workspace/diagnostic`: long-running; params `previousResultIds[]` (`uri` + `value`); result `WorkspaceDiagnosticReport.items`. Streaming may repeat a URI; last report wins. If document and workspace pulls overlap: higher document version wins; a document pull wins over a workspace pull.

**`Diagnostic`** (`diagnostic`, `diagnosticSeverity`, `diagnosticTag`, `diagnosticRelatedInformation`). `range`, optional `severity` (omit → client should treat as Error), optional `code`, optional `codeDescription.href` (since 3.16.0), optional `source`, `message` (`string | MarkupContent`; MarkupContent since 3.18.0, guarded by `textDocument.diagnostic.markupMessageSupport`, `@proposed`), optional `tags`, optional `relatedInformation` (`location` + `message`), optional `data` (preserved to `textDocument/codeAction`, since 3.16.0). Severity: `Error` 1, `Warning` 2, `Information` 3, `Hint` 4. Tags (since 3.15.0): `Unnecessary` 1, `Deprecated` 2.

## Workspace features

**Workspace folders** (`workspace_workspaceFolders`, `workspace_didChangeWorkspaceFolders`, since 3.6.0). Multi-root: `InitializeParams.workspaceFolders` when the client cap `workspace.workspaceFolders` is set. Server → client request `workspace/workspaceFolders` (no params) → `WorkspaceFolder[] | null` (`null` if a single file is open; empty array if a workspace is open with no folders). `WorkspaceFolder`: `uri`, `name`. Server cap `workspace.workspaceFolders` (`supported`, `changeNotifications`). Folder-change notification `workspace/didChangeWorkspaceFolders`.

**`workspace/configuration`** (`workspace_configuration`, since 3.6.0). Server → client pull. Params `ConfigurationParams.items[]` (`scopeUri?`, `section?`). Result `LSPAny[]` in item order; `null` entry if a setting cannot be provided. Replaces the old push model; servers that cache should still register for `workspace/didChangeConfiguration`. Client cap `workspace.configuration`.

**File operations** (`workspace_willCreateFiles`, `workspace_didCreateFiles`, `workspace_willRenameFiles`, `workspace_didRenameFiles`, `workspace_willDeleteFiles`, `workspace_didDeleteFiles`, since 3.16.0). Will-* are client → server requests that may return a `WorkspaceEdit` applied before the filesystem change (the edit cannot fill content of files about to be created). Did-* are notifications after the change. Client/server caps under `workspace.fileOperations.{willCreate,didCreate,willRename,didRename,willDelete,didDelete}`. Server registration uses `FileOperationRegistrationOptions.filters`. Clients may drop slow will-* results. Resource operations in edits (`resourceChanges`): `CreateFile` / `RenameFile` / `DeleteFile` with `kind`, URIs, options (`overwrite`, `ignoreIfExists` / `ignoreIfNotExists`, `recursive` on delete), optional `annotationId` (since 3.16.0). Names say “files” but operations apply to files and folders.

**`workspace/applyEdit` and `WorkspaceEdit`** (`workspace_applyEdit`, `workspaceEdit`, `textDocumentEdit`, `annotatedTextEdit`, `textEdit`). Server → client `workspace/applyEdit` (`ApplyWorkspaceEditParams`: optional `label`, `edit`, optional `metadata` since 3.18.0 with `isRefactoring?`) → `ApplyWorkspaceEditResult` (`applied`, optional `failureReason`, …). Client cap `workspace.applyEdit`. `WorkspaceEdit`: `changes?` (URI → `TextEdit[]`) **or** `documentChanges?` (`TextDocumentEdit[]` or mixed with create/rename/delete). If the client handles versioned edits and `documentChanges` is present, it is preferred. Resource operations in `documentChanges` execute in array order; `workspace.workspaceEdit.failureHandling` describes recovery. `changeAnnotations` map (since 3.16.0) referenced by `AnnotatedTextEdit` and resource ops; guarded by `workspace.workspaceEdit.changeAnnotationSupport`. `TextDocumentEdit`: `textDocument: OptionalVersionedTextDocumentIdentifier`, `edits: (TextEdit | AnnotatedTextEdit | SnippetTextEdit)[]` (non-overlapping; annotated since 3.16, snippets since 3.18 gated by `workspace.workspaceEdit.snippetEditSupport`). `TextEdit`: `range`, `newText`.

## Versioning and evolution machinery

**How 3.18 marks new work** (`whatIsNew`, Jekyll shell of `lsp-3.18-specification.md`). All new 3.18 features are tagged with since-version 3.18 text or JSDoc `@since 3.18.0`. The specification version groups features into a release and records first appearance. Compatibility is kept with capability flags exchanged at initialize. A detailed list is the change log at `version_3_18_0`.

**`proposed`** (HTML JSDoc `@proposed`; not a JSON field in the staged metaModel). Staged HTML marks `@proposed` on `FoldingRangeWorkspaceClientCapabilities.refreshSupport` (`workspace_foldingRange_refresh`) and `DiagnosticClientCapabilities.markupMessageSupport`. No `"proposed": true` property exists on requests/structures in `lsp-3.18-metaModel.json`.

**`since` in the metaModel.** `metaData.version` is `"3.18.0"`. Requests, notifications, structures, enumerations, type aliases, and nested properties carry optional `"since": "3.18.0"` (and older values). Examples of 3.18 `since` on requests: `workspace/foldingRange/refresh`, `textDocument/inlineCompletion`, `workspace/textDocumentContent`, `workspace/textDocumentContent/refresh`, `textDocument/rangesFormatting`.

**MetaModel as machine-readable protocol** (`metaModel`). Since 3.17 the project publishes `metaModel.json` (the 3.18 model), `metaModel.ts` (types for the model), and `metaModel.schema.json`. The staged JSON’s top-level keys are `metaData`, `requests`, `notifications`, `structures`, `enumerations`, `typeAliases`. A request entry typically has `method`, `typeName`, `result` (typed with `kind`: `or` / `reference` / `array` / `base`), `messageDirection` (`clientToServer` | `serverToClient`), optional `clientCapability` / `serverCapability`, `params`, optional `partialResult`, optional `registrationOptions`, `documentation`, optional `since`. Structures use `properties`, `extends`, `mixins`.

**Deprecation practice.** JSDoc `@deprecated` on superseded fields (`rootPath`, `rootUri`, `SymbolInformation`, symbol `deprecated` boolean in favour of `tags`, `rangeLength` in favour of `range`, `serverErrorStart`/`serverErrorEnd`). Using side of an enumeration should ignore unknown values and preserve them on round-trips (`enumerations`). Clients should ignore unknown server capabilities (`messageDocumentation`).

**Capability-gated backward compatibility.** New payload shapes are guarded by client capabilities (examples: `SnippetTextEdit` / `workspace.workspaceEdit.snippetEditSupport`; MarkupContent diagnostic messages / `textDocument.diagnostic.markupMessageSupport`; `LocationLink` / `linkSupport`; code-action literals / `codeActionLiteralSupport`). ## Implementation considerations the spec itself states

**Staleness / invalidation** (`implementationConsiderations`, `staleRequestSupportOptions`, `generalClientCapabilities`). Clients let users edit while requests are pending. Pattern: if client state changes in a way that invalidates a response, cancel and ignore (and resend if needed), **or** keep the request if the result can still be transformed. Servers should **not** auto-cancel merely because a state-change notification is queued; the older result may still be useful. If a server’s **internal** state change invalidates an in-flight result, it may error with `ContentModified`. Clients generally should not show that error in the UI; they may resend if they know how (position-based requests are called out as hard to re-craft). Clients should not send resolve requests for out-of-date objects (example: code lenses); a server may `ContentModified` those. `general.staleRequestSupport` (since 3.17.0): `cancel` (client will actively cancel) and `retryOnContentModified` (method names the client will retry after `ContentModified`).

**`ContentModified`** (`errorCodes`). Use when document content changed outside normal conditions. Do **not** use it only because a content-change message is still unprocessed; a result computed on older state might still help. If the client no longer wants the result, the client should cancel.

**Error recovery / crash.** If a server exits unexpectedly, the client should try to restart, but not endlessly (VS Code example: no restart after 5 crashes in 180 seconds). `willSaveWaitUntil` and will-file-operation results may be dropped if slow or repeatedly failing, to keep save/create fast.

**Request ordering obligations** (`messageOrdering`, `textDocument_didChange`). Apply `didChange` notifications in receive order and apply `contentChanges` in array order. Before issuing document-state requests, synchronize. Responses may reorder only when correctness is unaffected. After `shutdown`, only `exit` is allowed. `$/cancelRequest` still requires a response.

**Transport notes the spec states here.** Recommended CLI channel flags: `stdio`, `pipe` / `--pipe=`, `socket` / `--port=`, `node-ipc`. `--clientProcessId` should match `InitializeParams.processId` so the server can exit if the editor dies.

**Enumerations** (`enumerations`). Integer enums usually start at 1. Unknown values must not fail the using side.

## Unknowns

- No separate 3.17-to-3.18 upgrade-notes page was in the staged set. The 3.18 delta above is taken from `whatIsNew`, `version_3_18_0`, `@since 3.18.0` / `@proposed` in the HTML, and `"since": "3.18.0"` in the metaModel.
- Staged `metaModel.json` has no `proposed` boolean field. `proposed` is visible only as JSDoc `@proposed` in the HTML (folding-range refresh support; diagnostic markup-message support). Whether the unpublished `metaModel.ts` / `metaModel.schema.json` define such a field is not in the staged files (`metaModel` only links those siblings).
- MarkupContent on `Diagnostic.message` is marked since 3.18.0 and `@proposed` in the body, but is not listed under `version_3_18_0`. `SemanticTokenTypes.label` (since 3.18.0) is likewise absent from that changelog list.
- The Jekyll source `lsp-3.18-specification.md` is include directives after the “What’s new” prose; it is not spec text.
- `metaModel.ts` and `metaModel.schema.json` were not staged.
- The content-part sentence “protocol clients and servers must not send JSON-RPC requests” is adjacent to the batch-messages prohibition; the staged HTML does not say “batch” in that second clause.
- `UnchangedDocumentDiagnosticReport` requires `resultId`, but the spec does not further define how a client should behave if a server returns `unchanged` without a prior `resultId` (it only says a server can return `unchanged` if result ids are provided).
- How a client should combine push `publishDiagnostics` with pull diagnostics when a server offers both is not specified in the pull section (the overlap rule given is document-pull vs workspace-pull only).

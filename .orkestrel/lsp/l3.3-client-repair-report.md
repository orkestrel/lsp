# L3.3 client repair deviation report

## Result

The generation regression row was added and failed against the unguarded `1451e19` production
source at the intended wire observable. The prescribed guard then conflicted with the surrounding
transport-start catch: the catch converted its coded `closed` error into a coded `spawn` error.
The deviation contract stopped the unit. The conflicting production edit was removed exactly.

## Expected

After the transport start await, the prescribed generation guard was expected to prevent the stale
generation's `initialize` write and reject the stale `start()` promise with an `LSPError` coded
`closed`.

## Found

The `await this.#transport.start()` statement is inside a `try` whose `catch` converts every thrown
value into `new LSPError('The LSP transport could not start', { code: 'spawn', cause })`. Inserting
the prescribed guard directly after the await makes that catch convert the guard's coded `closed`
error to code `spawn`.

## Executed evidence

The red-first command against the unguarded production source was:

```text
npm run test:src:core -- tests/src/core/LSPClient.test.ts -t "does not initialize a superseded transport generation"
```

The command exited `1`. Vitest reported:

```text
AssertionError: expected [ …(2) ] to have a length of 1 but got 2
Tests  1 failed | 48 skipped (49)
```

The identical command after direct insertion of the prescribed guard exited `1`. Vitest reported:

```text
AssertionError: expected LSPError: The LSP transport could not sta… { …(2) } to match object { code: 'closed' }
-   "code": "closed",
+   "code": "spawn",
Tests  1 failed | 48 skipped (49)
```

The production guard edit was then removed exactly. No production source change remains.

## Done and not done

The existing transport fixture supports explicitly released deferred `start()` promises. The row
`does not initialize a superseded transport generation` drives exit-handler restart while the
earlier transport start remains pending. It asserts the stale promise's `closed` code and the
single `initialize` wire request.

The production guard is not done. The close-row rename, measured codes, code assertions, revert
probe, scoped regression floor, formatter check, linter check, and TypeScript check were not run
after the deviation.

Hypothesis: placing the ownership guard after the transport-start `try`/`catch`, before the next
`try`, would preserve the prescribed `closed` code while keeping genuine transport start failures
coded `spawn`.

## 1. Identity-collision carrier — BROKEN

The ambiguity rule closes for the two shapes the row pins, and then `#derive` corrupts a third that the previous round answered correctly.

What holds. `src/core/helpers.ts:1317-1319` marks a synthesized output returned for separate sources ambiguous, and `src/core/HTML.ts:315-318` stops the chain on that `undefined`, so `span` answers `undefined`. The reused-existing-node half reaches the same marking: for `<i>a</i><b>b</b>` with `page.map(node => node.category === 'text' ? existing : node)`, `outputs.get(existing)` is the first text node at the second text node's frame, `existing !== current`, so `derivations.set(existing, undefined)` fires and `tests/src/core/HTML.test.ts:195-198` is a real row, not a synthesized restatement. The identity rewrite keeps provenance: with no collision, `derivations` stays empty and `#derive` falls through to `this.#spans` (`HTML.ts:319-323`).

What breaks. `derivations` carries two different meanings on one key — "this node, as an output, came from X" and, when the handler hands back an original node, that same object's role as an *input* to some other rebuild. `#derive` at `HTML.ts:315-318` now consults `derivations` **before** `#spans` on every hop of the chain, not only on the first. So a chain that should stop at an original node's own span instead follows that node's output entry and lands on a foreign source.

Exact state, traced through the shipped code on `<i>a</i><b>b</b>` (parser spans: textA `{3,4}`, textB `{11,12}`):

```ts
const page = new HTML('<i>a</i><b>b</b>')
const [textA, textB] = page.filter(isTextNode)
const mapped = page.map((node) =>
	node === textA ? { category: 'text', value: 'A' } : node === textB ? textA : node,
)
const rewrittenA = mapped.find((n) => n.category === 'text' && n.value === 'A')
mapped.span(rewrittenA) // traced: { start: 11, end: 12 } — owed { start: 3, end: 4 }
```

- textA's frame: `rewritten` is the fresh `A` node, `outputs.set(A, textA)` (`helpers.ts:1317-1318`), `derivations.set(A, textA)` (`helpers.ts:1320-1322`).
- textB's frame: `rewritten` is textA, `outputs.get(textA)` is `undefined` so nothing is marked ambiguous — correctly, textA has exactly one output role — then `derivations.set(textA, textB)` (`helpers.ts:1320-1322`).
- `#derive` resolving `A` (`HTML.ts:310-325`): `derivations.has(A)` → textA; `derivations.has(textA)` → textB; `#spans.get(textB)` → `{11,12}`, written for `A`.

`A` derives from exactly one source and is not ambiguous, so it is precisely the case `guides/html.md:187` guarantees — "A one-source rebuild keeps that source region through `map`, `sanitize`, and `distill`" — and it receives the region of a character it never came from. That is worse than the absence this round was repairing: a plausible, wrong span, the same fabrication class claim 2 removed from `projectSpan`. It is also a regression against the H1 baseline, where `#spans` was read first and `A` resolved to `{3,4}`.

Reachability: `HTMLRewriteHandler` is `(node: HTMLNode) => HTMLNode`, the handler is caller-supplied through the public `map`, and returning a captured tree node is exactly what the shipped row at `HTML.test.ts:197` already does. No foreign contract implementation is needed.

What right looks like — smallest fix. Read the derivation entry once, at the output node, and restore the span-first order for the rest of the chain, so the ambiguity marker still wins where it must while a node's own span still terminates a deeper chain. In `HTML.ts:310-325`:

```ts
for (const node of walkNodes(document)) {
	visited.clear()
	let source: HTMLNode | undefined = derivations.has(node) ? derivations.get(node) : node
	while (source !== undefined && !visited.has(source)) {
		visited.add(source)
		const span = this.#spans.get(source)
		if (span !== undefined) {
			derived.#spans.set(node, span)
			break
		}
		source = derivations.get(source)
	}
}
```

That keeps `HTML.test.ts:189-199` green (the marker is read on the first hop) and returns `{3,4}` for `A`. Pin it with a row named for what it proves — a rewritten node keeps its own source region while a sibling source's original object is reused elsewhere — and run it red against the shipped `#derive` first.

What is **not** broken, so the fix stays bounded:

- The `outputs` clause itself is correct on both pinned shapes; do not widen it. The defect is in `#derive`'s lookup order, not in the marking.
- `sanitize` and `distill` are unaffected: `#cleanNode`, `#pruneRegion`, and `#keepContent` return `[node]`, fresh rebuilds, or `node.children`, and the `!child` guard at `helpers.ts:1546-1552` keeps spliced children out of `derivations`, so no original object ever acquires an output entry there.
- `pruneDocument` carries no `outputs` equivalent, so a caller-supplied prune handler returning one original node for a second source records a single source rather than ambiguity (`helpers.ts:1548-1552`). That path cannot reach `span`, which is why I do not raise it as a defect — but `guides/html.md:121` (the `pruneDocument` row) correctly claims only "record each one-source rebuild", so the guide does not overclaim it either. Record it for the successor round rather than repairing it now.

## 2. Uncovered-boundary carrier — CONFIRMED

`projectSpan` declares `HTMLSpan | undefined` at `src/core/helpers.ts:66-76` and returns `undefined` when either boundary misses the offsets array. The row that pins the exact former fabrication is `tests/src/core/helpers.test.ts:60-62`, transcribing PROBE B verbatim: `expect(projectSpan([0, 1], 1, 2)).toBeUndefined()`. Every internal call site records nothing on `undefined` — `parsers.ts` guards each of the text, comment, doctype, literal-`<`, popped-element, void-element, raw-text body, raw-text element, end-of-input, and document-root writes with `if (span !== undefined)`.

Attacks that failed: a negative index and a fractional index both miss the array and return `undefined`; the merged-text path at `parsers.ts:270-276` composes `start`/`end` from stored spans rather than re-projecting, so an uncovered boundary cannot enter through it. One adjacent behaviour is deliberately outside the claim and stays correct to leave alone: an inverted range (`start > end`) returns a span with `end < start` rather than `undefined`, because both boundaries are covered. That is a caller error on a documented half-open contract, it predates this change, and no shipped call site can produce it.

## 3. Recorder-mutation carrier — CONFIRMED

No public function accepts a mutable collection. A search of `src/` for `Map<HTMLNode` finds only local construction (`parsers.ts:45`, `helpers.ts:1250-1251`, `helpers.ts:1390`, `helpers.ts:1426`, `helpers.ts:1474`, `HTML.ts:289`, `HTML.ts:395`), the `#spans` field (`HTML.ts:71`), and `ReadonlyMap` in type positions (`types.ts:175`, `types.ts:187`, `HTML.ts:307`). `scanRawText` carries its region in the record it returns (`helpers.ts:508-540`, `HTMLRawText` at `types.ts:1053-1062` with every member `readonly`), and `rewriteDocument`, `collapseText`, `extractRegion`, and `pruneDocument` all return `HTMLDerivation` pairs.

Attacks that failed on the aliasing half: `parseProvenance` returns the map it built, but nothing mutates it after return and the `HTML` constructor copies it with `new Map(spans)` (`HTML.ts:75-77`), so `#spans` is never the parser's map; `span()` returns a fresh `{ start, end }` rather than the stored object (`HTML.ts:96-97`); `distill` copies before mutating (`HTML.ts:295`); `#keepContent`'s literal branch aliases its own empty local map into the returned pair (`HTML.ts:406`) and no caller mutates it. I found no returned map that a later call writes into.

## 4. Placement carrier — CONFIRMED

`parseProvenance` owns the sole walk and returns the readonly pair (`parsers.ts:43`, `types.ts:1035-1038`); `parseDocument` keeps `(html: string) => HTMLDocument` and reads the pair's document (`parsers.ts:33-35`), so there is one engine and no duplicated walk. `parsers.ts` exports exactly `parseDocument` and `parseProvenance`, both `parse*`. The mapping leaves live in `helpers.ts` as `normalizeSource` (`:37`) and `projectSpan` (`:66`), and `parseHTMLSource` / `parseHTMLSpan` return no match anywhere in the tree, verifying the report's old-name claim rather than trusting it.

The granted consumer files are lawfully untouched: `tests/setup.ts:113`, `tests/src/core/constants.test.ts:225-229`, and `tests/src/core/validators.test.ts:79` all call `parseDocument(source)` with one argument, which the unchanged signature still admits.

Attack that failed: I tested `parseDocument` as a superfluous wrapper, since it is a one-line delegate. It survives — it supplies a materially narrower contract (the document alone), it has real consumers that hold no use for spans, and removing it would either duplicate the walk or force every bare-document caller to destructure. The shape the successor brief offered is the one that shipped, and the guide names the distinction at `guides/html.md:86` and `:191`.

## 5. Control-discrimination carrier — BROKEN

The rows are named for what they prove: `HTML.test.ts:81` (parsed slice), `:99` (original coordinates), `:122` (absence), `:141` (propagation), `:182` (identity), `:189` (collision). That half holds.

The controls do not. The one control I can check from the supplied evidence is vacuous on its holding side. The host receipt (`h1.1.1-acceptance.md:20-31`) deleted `src/core/helpers.ts:1319` — `else if (source !== current) derivations.set(rewritten, undefined)` — and paired the red at `leaves a node returned for separate sources unprovenanced` with a hold at `carries root provenance through an identity map`. That line can only *add* an `undefined` marker, so deleting it can only cause *more* nodes to receive a span. No row that asserts a span is present can redden under it. The hold-side therefore cannot fail by construction, and the receipt's coverage sentence — "the row that must fail did, and the row that must hold did" — reads as discrimination the control cannot deliver. This is the H1 round's own claim-5 defect in mirror image: a control drawn from a population the mutation cannot reach.

What right looks like: pair that mutation with a row that asserts a span is **absent** for a reason other than reused identity — `returns undefined for adopted, foreign, and synthesized nodes` (`HTML.test.ts:122`) or the synthesized half of `HTML.test.ts:189-193` — because those are the rows a lost ambiguity marker would flip green-to-red in the direction the mutation actually moves. State the membership rule ("mutations that remove an ambiguity marker") before picking the control, then draw the control from outside it.

The remainder of this claim I could not check and am recording rather than ruling: the report's three in-sandbox accounts (`h1.1.1-provenance-repairs-report.md:25-27`) give counts only — "Propagation mutation: 1 failed, 1 passed" — and name no mutated line, so their consistency with the shipped diff is unverifiable, and a mutation leaves no trace in a diff for me to check it against. The scriptable scenario that would settle it: for each account, re-apply the named mutation on the host, run `npm run test:src:core -- --run` unfiltered, and record which rows redden across the whole file rather than in a two-row focused run — a focused run showing one red and one green cannot show that the family stayed green.

One consequence to carry into claim 1's fix rather than a separate carrier: `guides/html.md:187`'s guarantee that "A one-source rebuild keeps that source region through `map`" is false in the state claim 1 traces. The repair is the code, and the sentence becomes true when `#derive` is fixed. It needs no prose edit and must not receive one.
